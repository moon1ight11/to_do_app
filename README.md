## Возможности
-  **Аутентификация** — `JWT`-токены в HttpOnly cookies с валидацией кастомных полей
-  **Управление пользователями** — регистрация, обновление профиля, удаление с каскадным удалением задач и настроек
-  **Управление задачами** — CRUD операции, иерархия задач (подзадачи с рекурсивной загрузкой), отметка выполнения
-  **Пользовательские настройки** — управление временной зоной (UTC±X) и стандартной длительностью задачи
-  **Кэширование** — `Redis` (cache-aside pattern) для пользователей, задач и настроек с автоинвалидацией
-  **Мониторинг** — `Prometheus` метрики (RPS, latency, error rate, goroutines, memory) + `Grafana` дашборд
-  **Трейсинг** — `OpenTelemetry` с `Jaeger` (трейсы на всех слоях: HTTP → Service → Repository → Cache)
-  **Логирование** — структурированное логирование с уровнями INFO/ERROR/FATAL
-  **Контейнеризация** — `Docker`, `Docker Compose` для локальной разработки
-  **CI/CD** — `GitHub Actions` для сборки и публикации в `GitHub Container Registry`

## Технологический стек
- **Основной язык** - Go 1.25
- **HTTP-фреймворк** - Gin
- **Основная база данных** - PostgreSQL 15
- **Миграции базы данных** - Goose (автоматическое применение при старте)
- **Аутентификация** - JWT (golang-jwt) с кастомной валидацией claims
- **Безопасность** - bcrypt (cost factor = 10)
- **Тестирование** — testify (assert + mock), miniredis для кэша
- **Конфигурация** - Viper (YAML)
- **Кэширование** - Redis 7 (cache-aside с автоинвалидацией)
- **Профилирование** — `pprof` (CPU, memory, goroutines)
- **Мониторинг** - Prometheus + Grafana (готовый дашборд)
- **Трейсинг** - OpenTelemetry + Jaeger
- **Документация** — OpenAPI 3.0
- **Контейнеризация** - Docker, Docker Compose, GitHub Container Registry
- **CI/CD** - GitHub Actions
- **Архитектура** - Clean Architecture (handlers → services → repositories)

## Архитектура
Проект построен на принципах **Clean Architecture** с четким разделением на слои:
- **Handler / Delivery** — HTTP-обработчики (GIN)
- **Service / Usecase** — бизнес-логика приложения
- **Repository** — слой доступа к данным (`Redis`, `PostgreSQL`)
- **Domain** — модели, не зависящие от внешних фреймворков

## Быстрый старт
### Предварительные требования
- Go 1.25+
- Docker и Docker Compose

### Локальный запуск
1. **Клонировать репозиторий**
2. **Настроить конфигурацию**
```bash
    cp config.example.yml config.yml
    # В соответствии с config.example.yaml, создайте файл config.yaml, указав необходимые параметры
```
3. **Запустить инфраструктуру**
```bash
    docker-compose up -d
```
Будут запущены: PostgreSQL, Redis, Jaeger, Prometheus, Grafana
4. **Запустить приложение**
```bash
    go run cmd/main.go
```
Сервер будет доступен на http://localhost:8080.

### Доступ к сервисам
API: http://localhost:8080
pprof: http://localhost:8080/debug/pprof/
Prometheus: http://localhost:9090
Grafana: http://localhost:3000 (admin/admin)
Jaeger: http://localhost:16686

## Особенности реализации
### Кэширование
Реализована стратегия `cache-aside`:
- Кэшируются: отдельные пользователи, задачи, настройки и списки задач
- TTL: 10 минут для всех типов данных
- Graceful degradation: при недоступности `Redis` приложение продолжает работу, обращаясь напрямую к `PostgreSQL`
- Инвалидация: автоматическое удаление из кэша при создании, обновлении или удалении данных
- Ключи кэша:
    - user:{user_id} — данные пользователя
    - settings:{user_id} — настройки пользователя
    - task:{task_id} — отдельная задача
    - user_tasks:{user_id} — список задач пользователя

### Профилирование (pprof)
Приложение включает `net/http/pprof` для детального анализа производительности:
- **Интеграция в Gin:** pprof эндпоинты зарегистрированы как группа маршрутов `/debug/pprof/*`
- **Доступные профили:** goroutine, heap, allocs, block, mutex, threadcreate, profile, trace
- **Использование в разработке:** позволяет находить утечки горутин, избыточные аллокации и блокировки
- **Графический анализ:** поддержка flame graphs, call graphs и top-функций через `go tool pprof`

### Трейсинг
Распределенная трассировка с помощью `OpenTelemetry` и `Jaeger`:
- Автоматические спаны для HTTP-запросов через middleware
- Ручные спаны на всех слоях: Service, Repository, Cache
- Запись ошибок в спаны для быстрой отладки
- Контекст передается через все слои приложения
- Семантические атрибуты HTTP (method, route, status code)

### Graceful Shutdown
При получении сигнала завершения (`SIGINT`, `SIGTERM`) сервер:
1. Обрабатывает `panic` с логированием и корректным завершением
2. Прекращает принимать новые соединения
3. Ожидает завершения активных запросов (таймаут 10 секунд)
4. Корректно закрывает соединения с `PostgreSQL` и `Redis`
5. Закрывает файл логгера

### Логирование
- Структурированное логирование с уровнями `INFO`, `ERROR`, `FATAL`
- Запись логов в файл с автоматическим созданием директории
- Единый формат: [timestamp] LEVEL: message key=value key2=value2
- Логирование всех критических операций: вход, регистрация, CRUD операций

### Миграции базы данных
- Автоматическое применение миграций при старте приложения с помощью `Goose`
- Миграции включают создание схемы, таблиц и индексов
- Поддержка отката миграций (up/down)
- Индексы для оптимизации запросов: users(name), users(email), tasks(owner_id), tasks(completed_at)

### Транзакции и целостность данных
- Создание пользователя: атомарное создание пользователя + дефолтных настроек
- Удаление пользователя: каскадное удаление настроек и задач
- Обновление пользователя: транзакционное обновление имени/почты/пароля
- Удаление задачи: рекурсивное удаление всех подзадач через `SQL CASCADE`
- Обновление задачи: атомарное изменение нескольких полей
- Все транзакции с автоматическим откатом при ошибках

### Безопасность
- Пароли хэшируются с помощью `bcrypt` (cost factor = 10)
- `JWT`-токены хранятся в HttpOnly cookies с флагами Secure и HttpOnly
- Валидация кастомных полей `JWT`: UUID пользователя, email (regex), непустое имя
- Защита от атак с неправильной подписью и истекшими токенами
- Настроены политики `CORS` для безопасного взаимодействия с фронтендом
- Валидация всех входных данных (email, временные зоны, UUID)

## Покрытие тестами
- Модульные тесты: `JWT`-сервис (генерация, парсинг, валидация), кэш (полный жизненный цикл)
- Библиотеки: `testify` (assert + require), `miniredis` (эмуляция Redis для тестов)
- Особенности:
    - Тесты `JWT` проверяют все сценарии: правильный токен, неправильная подпись, истекший срок, неверный метод шифрования
    - Тесты кэша используют `miniredis` для изоляции от реального `Redis`
    - Полное покрытие всех методов кэша: Set, Get (успех + cache miss + expired), Delete

## Мониторинг
Сервис экспортирует метрики для Prometheus на эндпоинте /metrics
**RED метрики (Rate, Errors, Duration):**
- `http_requests_total` — счетчик HTTP-запросов (method, endpoint, status)
- `http_request_duration_seconds` — гистограмма длительности запросов (method, endpoint)
- `http_requests_in_flight` — текущее количество обрабатываемых запросов

**Бизнес-метрики:**
- `app_operations_total` — счетчик бизнес-операций по типам
- `app_errors_total` — счетчик ошибок по типам (`bad_request_error`, `forbidden_error`, `internal_error`) и обработчикам

**Инфраструктурные метрики:**
- `go_goroutines_count` — количество горутин
- `go_memstats_alloc_bytes` — использование памяти
- `go_gc_duration_seconds` — длительность сборки мусора

**Готовый дашборд для Grafana** включает 9 панелей:
1. RPS (Requests Per Second) по эндпоинтам
2. Error Rate (4xx + 5xx)
3. P95 Response Time
4. Active Requests
5. Количество Goroutines
6. Response Time by Endpoint (P95)
7. Business Errors по типам и обработчикам
8. Memory Usage
9. GC Pause Time

## Контейнеризация
Docker Compose включает:
- `PostgreSQL 15` — основная база данных (порт 15432)
- `Redis 7` — кэширование (порт 6379)
- `Jaeger` — распределенная трассировка (UI: 16686, gRPC: 4317)
- `Prometheus` — сбор метрик (порт 9090)
- `Grafana` — визуализация метрик (порт 3000, admin/admin)

Все сервисы объединены в сеть `monitoring` для безопасного взаимодействия.

## CI/CD
GitHub Actions настроен на:
1. Сборку Docker-образа при ручном запуске (workflow_dispatch)
2. Публикацию образа в `GitHub Container Registry` (ghcr.io)
3. Тегирование образа как `latest`
